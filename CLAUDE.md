# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

CUDA/C++17 phase-field solver for a 2D phase transition (anisotropic Allen–Cahn-type equation for the phase `p`, coupled with diffusion of the Nb concentration `c` in a Zr–Nb alloy). It is research code for a thesis at FNSPE CTU Prague. Python scripts post-process and plot the results. Comments and messages are in English.

## Build & run

The code needs `nvcc` and the header-only **TNL** library (Template Numerical Library). The build uses the system TNL in `/usr/include/TNL`; the Makefile's `-I~/.local/include` is never tilde-expanded, so it does nothing (on the cluster `~/.local/include/TNL` is an old 2022 copy without `ODESolver.h`, so "fixing" the tilde would break the build). Builds only work on a Linux machine with an NVIDIA GPU. The Makefile compiles with `-arch=native` (override with `make CUDA_ARCH=...`) and keeps objects in `build/sm_<compute capability>/`, so build on the machine that will run the binary. Jobs for the GPU cluster are submitted from a local machine with `slurm/cluster.sh` (see `slurm/run.sbatch`); from Windows PowerShell use the launcher `.\slurm\cluster.cmd`, which runs the script with Git's bash and Windows OpenSSH (the key lives in the Windows ssh-agent).

```bash
make                                  # build ./build/Phase-field
make run FOLDER=MyRun MODEL=Zr-H_Ma2002   # build, run config/Zr-H_Ma2002.json -> results/MyRun, then plot
make run FOLDER=MyRun CONFIG=path.json    # the same with any config file (MODEL or CONFIG is required)
make run FOLDER=MyRun MODEL=... DELETE_CALCS=1  # same, but keep only the first and last Result-*.npy afterwards
make run_all                          # run every comp_configurations/*.json (passed as CONFIG=)
make clean
```

- **One config per model** (2026-11-23): `config/<model.type>.json` (`allen_cahn.json`, `Zr-Nb_Choud2013.json`, `Zr-H_Ma2002.json`) is a complete config (`solver`, `init_cond`, `bound_cond`, `model` with only that model's section), because the models need very different domains, times and resolutions. There is no default config and no `config/config.json` any more: the run names its config, `make run MODEL=<name>` (= `CONFIG=config/<name>.json`) or `CONFIG=<file>` (both or neither: the Makefile stops before building, listing the models), `cluster.cmd submit NAME --model <name>` or `--config FILE` (likewise). The binary is called as `Phase-field RESULT_FOLDER CONFIG_FILE` (both required). The configs in `config/` are inputs, not code: they do not make a commit `-dirty` and do not count for `test`'s same-code check. `slurm/cluster.sh submit` uploads the sources of each run, with the chosen config as `config/config.json` (the name the job runs; only inside the archive), to `jobs/<FOLDER>/sources.tar.gz` on the cluster. The job unpacks them into the node's `/tmp`, gets the binary from `slurm/cached_build.sh` and runs `make run BINARY=...` there, with `results` linked to the shared results folder. A queued job therefore always runs the code it was submitted with, and jobs share no sources.
- Build cache (2026-11-20, all three modes: `run.sbatch` exports `BUILD_CACHE`, and `build()` in `tests/common.sh` then calls the harness's `cached_build.sh` for both versions of `test`/`bench`, any commit; without `BUILD_CACHE` it builds as before; a test whose both versions were cached took 61 s instead of 2:15): `cached_build.sh` hashes every uploaded file except `config/ python/ tests/ slurm/ results build/ comp_configurations/ *.md .git* requirements.txt` (an exclusion list on purpose: old commits had sources in the top folder, so an unknown file only causes a needless build), plus the compute capability, `nvcc --version`, the gcc version and the contents of `/usr/include/TNL`. A hit (`build_cache/sm_XX-KEY/Phase-field` in the cluster folder) is copied to the node and nothing is compiled; a miss builds with `make -j $SLURM_CPUS_PER_TASK -O` and stores the binary (copy under a temporary name + rename, so racing jobs are harmless, and that race did happen in the first test; a failed store never fails the run). Entries hold `info.txt` (node, GPU, job, run, commit) and `last_used` (the time of the last use as its content, written to a new file and renamed: a `touch` from a compute node never reaches gp3 over NFS, the node alone sees the new time); `cluster.sh cache` lists them, `cache prune [--days N]` (default 30, 0 = all) deletes the unused ones. An entry is ~3.7 MB. The job log says `Build cache: using ...` or `nothing for ... yet, building`. Measured on gp13: build 88 s serial, 78 s with `-j 2` (only that little: the cluster allocates whole cores, `CR_CORE`, so `--cpus-per-task=2` is one physical core with its 2 hyperthreads), 0 s on a hit. `make run` without `BINARY` builds and runs `build/sm_XX/Phase-field` as before. gp3 has no `hostname` command (use `$HOSTNAME`).
- Run everything from the repo root. The binary resolves its default config through a relative path, and the Python scripts look in `./results/<name>`.
- Header dependencies are tracked: nvcc writes `build/sm_XX/*.d` (`-MMD -MP`) and the Makefile includes them, so changing a header under `include/` recompiles the objects that use it. System headers (TNL in `/usr/include`) are not tracked. `make clean` is still needed after changing compiler flags in the Makefile or after updating TNL (not on the cluster, where every job builds in a fresh copy, and the build cache key contains the Makefile and TNL). (Before this, stale `.o` files after header changes caused hard-to-find bugs.)
- Several runs on the cluster: `cluster.cmd submit-many [FOLDER|FILE...] [--prefix P] [--dry-run]` (default folder `comp_configurations/`; give a folder, PowerShell does not expand `*.json`) submits one ordinary run and job per config, named P + file name without `.json`, so `status`/`list`/`cancel`/`fetch` work unchanged. It checks everything first (JSON, names valid, distinct and free on the cluster, GPU type) and submits nothing if a check fails; `--delete-calcs`, `--force`, `--gpu`, `--mem` as for `submit`. One run: `submit NAME --model M` or `--config FILE`. Both put the file into the uploaded archive as `config/config.json` (`pack_sources` in `cluster.sh`) and never touch the local one; relative paths are relative to the folder the script was started from (it must still be inside the repo). No throttle on purpose (the user's choice): all jobs are queued at once. A firewall in front of gp3 drops new ssh connections that come in quick succession (found 2026-11-20: ping loses nothing, but connections often need TCP retries, and the old submit-many, with an upload and an sbatch connection per run, failed with `Connection timed out` on its 6th connection). So every ssh call goes through `cssh` (`ConnectTimeout=10`, `ConnectionAttempts=4`), and submit-many sends all archives plus a generated `submit.sh` as one tar over a single connection (at most 3 connections in all: `--gpu` check, name check, upload + sbatch); `submit.sh` submits the runs in order, prints `SUBMITTED name id` per run and on an sbatch failure stops and deletes the uploads of the runs not submitted. Keep the number of ssh connections of a command small.
- From 6db179f until submit-many (2026-11-19), `cluster.sh submit` passed `MODE=submit`, which `run.sbatch` rejects (`Unknown MODE 'submit'`), so every plain submit in that period failed at the start of the job; `sbatch_run` now maps it to `run`. `test` and `bench` were not affected.
- `make run_all` (local only) runs every `comp_configurations/*.json` with `CONFIG=`. `comp_configurations/` is gitignored, apart from `.gitkeep`, so it is never uploaded: use `submit-many` on the cluster.
- There is no linter. There is a regression test and a benchmark (see below).

## Regression test

It answers "did my change alter the results?", not "are the results correct?" (that is the job of a comparison with the analytic solutions).

```bash
.\slurm\cluster.cmd test MyTest                     # working tree (uncommitted changes) vs HEAD
.\slurm\cluster.cmd test MyTest --against HEAD~1    # vs any commit, e.g. after committing the changes
.\slurm\cluster.cmd test MyTest --against A --new B # two commits: B is tested instead of the working tree
.\slurm\cluster.cmd status                          # while it runs: which build or run it is at
.\slurm\cluster.cmd log                             # the result; also in results/MyTest/report.txt
```
- `cluster.sh test` uploads the working tree (like `submit`) plus `git archive <commit>` as the baseline, and refuses when both have the same code (the configs in `config/` do not count). So test **before** committing, or use `--against`.
- `--new COMMIT` (test and bench) uploads that commit as `new.tar.gz` and tests it instead of the working tree. The working tree is still uploaded as the harness: `run.sbatch`, `tests/`, the configs and `python/compare_*.py` always come from it (`harness_dir` in `tests/common.sh`), so commits from before the test existed can be compared too, as long as they accept `Phase-field RESULT_FOLDER CONFIG` and write `info/setup/parameters.txt` (98e885c or later).
- The job (`run.sbatch` with `MODE=test`, time limit 1 h) runs `tests/regression.sh`: it builds both versions (or takes them from the build cache), runs every test case (`tests/configs/*.json`, or the version's config set, see below) with both on the same GPU (so GPU-type differences cannot appear) into `results/MyTest/{base,new}/<case>`, then runs `python/compare_runs.py`. Nothing is stored in the repo; the baseline is recomputed every time. The configs, scripts and comparison come from the new version.
- **Config sets** (2026-11-23; before, the test configs carried the old sections next to `model` and the solver only warned about unknown keys): each version runs the test and benchmark configs in the layout its code reads. The current ones are `tests/configs`, `tests/benchmark_configs` and `tests/benchmark_configs_long`; an older layout is kept in `tests/config_sets/up_to_<C>/` (the same subfolders) for the commit C and the commits before it. `config_set_of` in `cluster.sh` picks for the baseline and for `--new COMMIT` the set with the oldest such C (`git merge-base --is-ancestor`), or the current configs; the working tree always gets the current ones. It passes them to the job as `BASE_CONFIG_SET`/`NEW_CONFIG_SET` (empty = current), `config_folder` in `tests/common.sh` finds them in the harness. A case that the baseline's set does not have is skipped; the top of `report.txt` names both sets and the skipped cases. `compare_runs.py` lists the layout differences as `config differs` notes. The sets: `up_to_12df4ec` (98e885c … 12df4ec) is the test configs as they were before 2026-11-23, the old sections (`problem`, `force_term`, `anisotropy`) and the `model` sections both (the files that were tested against old commits; the harness needs `model`: `prepare_input.py` reads `model.type`); `up_to_2ce1df9` (2d32cad, 2ce1df9) and `up_to_cf625cb` (a2dfcdf … cf625cb) are the test configs those commits shipped with (`git show`): the model named `zirconium` in the first, and no `solver.adaptivity` in either (cf625cb rejects it, the others ignore it; TNL's default is the same 1e-05). All three were checked to hold the same problems as the current configs and have no `hydride`. So every commit from 98e885c on can be a baseline; older ones write `parameters.txt` into `info/` and no computation time, which the harness no longer reads. Expected failures: `from_file` against double builds (before 5e9bccb, they read only double frames, the input is float32), and float vs double differences before 5e9bccb. **When a change makes HEAD unable to read the current configs** (a new required key, since an unknown key is an error; a renamed or removed key): first copy `tests/configs`, `tests/benchmark_configs` and `tests/benchmark_configs_long` to `tests/config_sets/up_to_<short hash of HEAD>/`, then change the current ones. A changed parameter of a test case belongs into every set that has the case, otherwise an old baseline computes another problem.
- Cases (5 frames, seconds each): `circle_constant` (isotropic, constant force; 120×100 on [0, 1.5] × [0, 1], so hx ≠ hy and a mistake in the IC coordinates shows), `wulff_radial` (anisotropy, Wulff IC, radial force), `zirconium` (the `Zr-Nb_Choud2013` model, concentration), `dirichlet_mixed` (Dirichlet and Neumann for both fields), `from_file` (IC from a float32 `.npy` file with `scaling`, generated by `tests/prepare_input.py`), these four 100×100 on the unit square; `random_rectangle` (120×80 on [-0.5, 1.5] × [0.2, 1]; random values at every point from `random.npy`, without scaling, zirconium, all Neumann); `hydride` (the `Zr-H_Ma2002` model, 80×60 on [0, 79] × [0, 47.2], so hx = 1 ≠ hy = 0.8 in the article's grid units; random phase in [0, 1] and concentration in [0, 0.7] from `random.npy`, `prepare_input.py` chooses the range by `model.type`; phase Dirichlet in x; `final_time` 1; `custom_integration_time_step` 0.001: the default min(h)²/5 = 0.128 is far beyond the explicit stability limit of Cahn–Hilliard, the first step's error estimate is ~1e19, the single rejection shrinks τ to ~1e-6, and TNL never lets it grow again (see Time stepping), so the case ran over 10 min; with 0.001 it takes 200 steps per frame). Against a baseline from before the equations (HEAD of 2026-11-23 and older) `hydride` is DIFFERENT or FAILED, as expected. The other cases start with a constant phase near the edges, so a wrong boundary index would barely show in them (during the run the interface tail reaches the bottom edge in `circle_constant` and the grain reaches the edges in `zirconium`, so the boundary treatment does affect them); `random_rectangle` catches it (`prepare_input.py` writes random values for any `random*.npy`). Keep at least one case with hx ≠ hy, otherwise swapped x and y go unnoticed. Each case should run a different code path; add a config for a new feature.
- Verdicts: IDENTICAL (bitwise), CLOSE (phase difference and concentration difference relative to its range ≤ `--tol`, default 1e-4, and no cell crossed 0.5), DIFFERENT, FAILED (missing, unfinished or NaN), INCOMPATIBLE (different grids). Cleanup should give IDENTICAL; reordered arithmetic (performance work) at best CLOSE. For reference, float vs double on the 200×200 zirconium run differed by 3.5e-4 in the phase after 100 frames.
- The test draws no plots. After `cluster.cmd fetch MyTest`, `python3 python/basic_plot.py --name MyTest` plots every run in it (it does that for any `--name` folder that is not a run itself but contains runs); one case: `--name MyTest/new/zirconium`.
- `python3 python/compare_runs.py results/A results/B` compares any two runs (or two folders of runs) the same way, e.g. two `submit` runs on different GPUs.

## Benchmark

It answers "how much faster is my change?". Built like the regression test: working tree vs a baseline commit, both on the same GPU, nothing stored in the repo.

```bash
.\slurm\cluster.cmd bench MyBench                          # working tree vs HEAD, 3 runs of each version per case
.\slurm\cluster.cmd bench MyBench --against HEAD~1 --repeat 5 --gpu rtx3060
.\slurm\cluster.cmd bench MyBench --against 5e9bccb~1 --new 5e9bccb   # two commits, e.g. an old change
.\slurm\cluster.cmd bench MyBench --long                   # one demanding case, one ~10 min run of each version
.\slurm\cluster.cmd log                                    # the result; also in results/MyBench/report.txt
```
- The job (`run.sbatch` with `MODE=bench`, time limit 1 h + 15 min per run above 3) runs `tests/benchmark.sh`: it builds both versions (or takes them from the build cache) and runs every `tests/benchmark_configs/*.json` (or the version's config set, as for the regression test) N times with each, alternating the order (base new, new base, …), so a drift on the node hits both alike. `tests/common.sh` holds the build and run functions shared with `regression.sh`.
- Time = the solver's own `Computation time` from `parameters.txt` (time loop including frame writing, without start-up and IC). A run without it counts as failed. `python/compare_times.py` reports median (fastest–slowest) per version and the speedup base/new (> 1: new is faster; `~` = the ranges overlap, i.e. within the noise), and the geometric mean over the cases. It also reads `Integration steps` from each run's `parameters.txt` (`-` for versions from before the step count, i.e. up to 2f0ab0f) and shows the steps of both versions and the per-step speedup (time per accepted step, base/new), so a speedup from fewer adaptive steps can be told from cheaper steps; it notes when the repetitions of one version took different numbers of steps.
- Output in `results/MyBench/`: `times.csv` (every run), `report.txt`, `{base,new}/<case>` (first run, complete) with `comparison.txt` from `compare_runs.py` (a speedup only counts if the results still agree), `repeats/` (the other runs, without frames).
- Cases (about half a minute each on an RTX 2070 SUPER, scaled from Bench_noise, where the runs of one case differed by ≤ 1 %): `zirconium_200` (the production config, shortened: the time per frame is constant during a run), `zirconium_400` (the same at 400×400), `wulff_radial_300` (anisotropy and radial force, no concentration; the Wulff shape shrinks and would vanish at t ≈ 0.055, so its length comes from the resolution, not from `final_time`). The time scales linearly with `final_time` and roughly as h^-3.5 with the grid.
- `--long` runs `tests/benchmark_configs_long/*.json` instead (passed on as `BENCH_SET=long`): `zirconium_400_sharp` (zirconium at 400×400 with a thin interface, `ksi` 0.0125 instead of 0.075, `theta_0` 0.1, `final_time` 0.02, 4 frames; measured 8.7–8.9 min per run on an RTX 2070 SUPER in LongBench, about 130 s per frame. The grain grows into a cross that almost touches the edges at t = 0.02, so do not lengthen `final_time`: raise the resolution instead), once with each version by default (`--repeat N` for more), time limit 30 min + 30 min per repetition, timeout per run 40 min instead of 10. It shows whether a speedup holds for a long, demanding run.
- Unlike `test`, `bench` runs when both versions have the same code: that shows the noise. Times depend on the GPU type, so compare speedups, or use `--gpu` to benchmark on the same type.

Plotting (it runs from the repo root and needs `results/<name>/info/setup/config.json`):
```bash
python3 python/basic_plot.py --name MyRun --type both   # selected frames + animations (mp4, or gif without ffmpeg) into results/MyRun/info/plots/
python3 python/basic_plot.py --name MyRun --frames 0 50 last --format gif
python3 python/plot.py --name MyRun --frame 10 --type phase   # --frame last works too, --no-save opens a window instead of saving
```
`python/graphs/*.py` are standalone scripts for thesis figures. They use LaTeX text rendering.

Errors against a reference run (convergence study, work in progress since 2026-11-19): `python3 python/lp_errors.py RUN REFERENCE [--eval-cells NX NY] [--output FILE]` is the Python version of `Measurement/JK/lp_dist_new_new.pas` (the user's old Pascal tools in `Measurement/`, untracked, 4.8 GB: never `git add` the folder). It interpolates both runs bilinearly (Pascal's `Inter1`/`Inter2`, bit for bit, incl. the zero node behind the edge), evaluates the difference on the evaluation grid (default: lcm of the cell counts, which makes L∞ exact; error if it is more than 4x the finer grid), L∞ = max, L2 = trapezoidal rule (weights 1, 1/2, 1/4; the user chose to keep it, not the exact Q1 mass-matrix integral), per frame for phase and concentration (not for `allen_cahn`), then max over the frames (Pascal's L∞(0,T; ·)) and L2 in time (trapezoidal over the frames, an addition). Strict checks: domain, initial/final time, frame_num, model type, both runs finished and complete, no NaN; only the current config layout (since 2026-11-23 nothing reads old results). Differences in the settings the solver uses (`used_settings`: `solver`, `init_cond`, `bound_cond`, `model.type`, `model.<type>`, minus `integration_time_step` when `custom_integration_time_step` is false and the file path/`scaling` when `init_cond_from_file` is false; e.g. `ksi`) and a reference that is not finer only warn; a setting used in one run only is a difference too. Checked on synthetic runs against a literal loop transcription of the Pascal code (≤ 3e-15 relative) and, on 2026-11-19, against the real programs on gp3 (synthetic runs, 30x20/60x40/120x80 vs 240x160, lcm and 700x450 evaluation grids): lp_errors vs `Measurement/JK/lp_dist_new_new` (old static i386 FPC 2.2.2 binary; there is no Free Pascal compiler anywhere, not even on the cluster) ≤ 1.2e-13 relative, eoc.py vs eoc.cpp ≤ 6.4e-8. Unpatched `eoc.cpp` is broken with GCC 16: `%ld` into `int n2` overwrites h, so every EOC is NaN (the old eoc.tex files show N_T = 0 from the same bug); the test used a copy with `long n2`. The evaluation grid changes the errors and even the EOC (2.05 vs 2.24 for the last pair), so keep it the same within a study. `python3 python/eoc.py RUN1 RUN2 ... --reference REF [--eval-cells NX NY] [--output FILE] [--tex FILE]` is the Python version of `Measurement/eoc.cpp`: runs from the coarsest to the finest (checked before the errors are computed), errors from `lp_errors.compute_errors`, per field a table of errors (h = max(hx, hy), accepted integration steps, DoF = 2·sizeX·sizeY, the 4 norms, computation time; no ξ column, the user's choice) and a table of EOCs, `EOC_i = log(e_i/e_{i-1}) / log(h_i/h_{i-1})`, `-` where undefined; LaTeX without packages or macros. `eoc_column` reproduces `Measurement/Test/eoc.tex` to 1.2e-7 (eoc.cpp reads float). The check scripts live only in the scratchpad (not in the repo).

Hausdorff distance of the interface (2026-11-19): `python3 python/hausdorff.py RUN REFERENCE | RUN --analytic [--spacing S] [--output FILE]` is the counterpart of `Measurement/hausdorf.pas`, with **shapely** (the user's choice; 2.2.0 locally and on the cluster as the Arch package `python-shapely`; no other method on purpose, a precise one is postponed). Per frame: the level 0.5 of the phase from `Boundary.numerical_curves` (all curves of the frame), against the reference run's (the checks of `lp_errors.py`) or, with `--analytic`, against `analytic_polyline` (allen_cahn, ConstantCircle/Circle/WulffShape not from a file, force constant 0 or radial; elapsed time = frame·time_step) as a polygon within 1e-10 × the shorter side of the curve (midpoint-to-chord estimate, doubling from 1000 segments), clipped to the domain (warning). d_H = what `shapely.hausdorff_distance(segmentize(A, δ), segmentize(B, δ))` gives (the discrete GEOS distance: sample points vs the whole other polyline, both directions), δ = S·max(hx, hy), S = 0.01, but computed with `STRtree.query_nearest` (GEOS's own is all-pairs: 7 s per frame at 600 vs 4600 points); polylines with segments much shorter than δ (the analytic polygon) keep every k-th vertex as samples. True distance of the polylines ≤ d_H + δ/2; every frame is recomputed with 2δ and a change above 1 % warns. One curve empty: error naming the frame; both empty: 0. Norms in time: max and L2 (trapezoidal). No eoc.py table (user: not now). `write_boundary_files` joins the curves of a frame without a separator, so `hausdorf.pas` would connect them by a spurious segment. Checked in the scratchpad: equals `shapely.hausdorff_distance` to 3e-17; exact circle contours converge at EOC ≈ 2.1, the Wulff shape (corner curvature 50) at ≈ 2 from 200 cells; on [-0.5, 1.5] × [0.2, 1] (hx ≠ hy) the circle converges too, shifts along x and y alone stay within the triangle-inequality bound, θ0 = -0.3 instead of 0.3 is 200× off; several curves per frame and open curves at the edges equal shapely to 5e-17; initial_time ≠ 0 uses the time since the IC; vs a literal Python transcription of `hausdorf.pas` (no compiled binary exists) on single-curve frames: equal to 1e-15 for two runs, ≤ 1e-6 relative vs the analytic polygon (Pascal samples all its vertices, we thin them). Timing: 200 vs 1600 cells 0.9 s per frame, 1600 cells vs analytic 11 s per frame (the cost grows with 1/δ). First real study (2026-11-20, allen_cahn Wulff radial, ξ = 0.01, 200/300/500 vs 800, `adaptivity` 1e-5): frame 0 is the kinked linear-ramp IC sampled on each grid (first order, it sets L∞(0,T; L∞)); frames 1–10 converge at ≈ 2; late frames stagnate because the time error of `adaptivity` 1e-5 (vs 1e-7: L2 2.5e-3, d_H 6.2e-4 at t = 0.03, erratic in time) exceeds the grid error, so convergence studies need a much stricter `adaptivity`; against the analytic solution the distance is ≈ 0.2–0.4 ξ (ξ must shrink with h).

## Architecture

**Source layout:** `include/` and `src/` have the same subfolders, by function: `core/` (`types.hpp`, `Grid.hpp`, `constants.hpp` (`pi`, `R`, `Cal_to_joule`, `Phase`), `warnings.hpp`: `warn(message)` prints `Warning: ...` to stderr and keeps it, so `start` writes the warnings into `parameters.txt`; use it for every host warning that belongs to the run), `config/` (`Parameters`, `ConfigSection`, `enums`), `models/` (`Model`, `AllenCahn`, `ZrNbChoud2013`, `ZrHMa2002`, and `thermodynamics/` with the data of the alloy systems, `ZrNbThermodynamics`), `initial_condition/` (`InitialCondition`), `io/` (`ResultIO`, `RunFolder`) and, only in `include/`, `external/` (the third-party `json.hpp`, `npy.hpp`); `src/main.cu` stays at the top. Headers are included with their folder, relative to `include/` (`#include "models/Model.hpp"`, also for `json.hpp`). The Makefile finds the sources in all subfolders and mirrors them in `build/sm_XX/`; a new `.cu` file needs no Makefile change.

**Data flow:** `config/<model>.json` (or any config file) → `Parameters::load` → a model (`AllenCahn`, `ZrNbChoud2013` or `ZrHMa2002`) + `InitialCondition` → TNL `ODESolver` (adaptive Kutta–Merson) loop in `src/main.cu` → `write_frame` (`src/io/ResultIO.cu`) → `results/<FOLDER>/calculations/Result-NNNNN.npy` → Python plotters.

**State vector:** there is a single TNL `Vector` `u` of length `2*sizeX*sizeY` that lives on the CUDA device. Phase values are in `[0, N)` and concentration values in `[N, 2N)`, with `N = sizeX*sizeY` and linear index `j*sizeX + i`. Use `Model::phase_at` / `conc_at` to read them.

**Grid (`include/core/Grid.hpp`):** a plain struct with `sizeX`, `sizeY`, `domain` and the steps `hx`, `hy` (computed once by its constructor), plus `num_points()` (= N), `index(i, j)` and the coordinates `x(i)`, `y(j)`. It is built from the config by `Parameters::grid()`, held by the model and `InitialCondition` and passed to `write_frame`/`read_frame` and the IC setters. Use it instead of writing the index arithmetic or computing h again.

**Time stepping (`main.cu`):** the RHS lambda is evaluated with `parallelFor` on interior points only. Boundary conditions are separate `parallelFor`s that run after it and set only `fu` on the boundary: Dirichlet `fu = 0`, Neumann `fu` = the `fu` of the neighbouring interior point. They never write `u` (the solver passes temporary stage vectors to the RHS, so writes into `u` would lag one time step). This keeps the boundary consistent only if it is consistent at the start, so `set_init_cond_boundary` (`src/initial_condition/InitialCondition.cu`) applies the boundary conditions to the initial condition (Dirichlet values: phase 0, concentration `c_phase_0` of the model's `InitialConcentrations`); bottom/top run before left/right in both places, so the corners match. The outer loop counts frames (`i = 1..frame_num`, so it always ends, whatever the rounding of the solver time): it sets the stop time `initial + (final-initial)*i/frame_num` (computed from `i` in double, exactly `final_time` for the last frame), solves up to it and writes one file per frame. Frame numbers are absolute, `round(initial_time/timeStep) + i` with `timeStep = (final-initial)/frame_num`, so a run continued from a file carries on with the numbering; the progress line counts `i`. Unless `custom_integration_time_step` is set, the integration step defaults to `min(hx,hy)^2/5`; it is only the initial step, Kutta–Merson then adapts it with the tolerance `solver.adaptivity` (`setAdaptivity` in main.cu; a step is accepted when tau * max|error estimate| < adaptivity; 0 = no adaptivity, a fixed step). **The step never grows** (found 2026-11-23): in TNL's `ODESolver::iterate` (dynamic version, `/usr/include/TNL/Solvers/ODE/ODESolver.hpp`) an accepted step calls `updateSolutionAndResidue()`, which ends with `setTau(finalTau)` (the step it entered with), and only then computes the larger `newTau` into the local `finalTau`, which is discarded at `break`. So the step only shrinks on rejections and keeps its value across `solve()` calls: a run uses the step left after its first rejection(s), which depends on the initial step and the first frame's length (the first attempt is clipped to the frame's stop time). The user chose not to fix it for now (only `tests/configs/hydride.json` got a small custom step); keep it in mind for timings and convergence studies. All configs use 1e-05, TNL's own default (`RealType adaptivity = 0.00001` in ODESolver.h), so results equal those from before the key existed; older commits ignore the key (they read these sections leniently, or warn about unknown keys), except cf625cb, which rejects it. A stricter value is for reference runs (accuracy tests, convergence study). After every written frame (and the initial one) `check_frame_finite` counts NaN/inf values on the GPU (one reduction per field); if there are any, it writes `Run failed: ...` into `parameters.txt` and the binary exits with `EXIT_RUN_FAILED` (2), keeping the broken frame. `make run` then still appends the commit and plots with `--force` (basic_plot.py refuses incomplete runs otherwise), skips `DELETE_CALCS` and fails with 2; any other non-zero exit stops `make run` at once. Exceptions never reach `std::terminate`: `main` catches them and prints `Error: ...` (exit 1; mostly config errors, before the run folder is created); after `RunFolder::create`, `start` catches them too and records `Run failed: unexpected error: ...` (exit 2 once the time loop has started, so the frames are plotted, else 1). A frame that `write_frame` cannot write (full disk, quota, missing folder) also stops the run, with `Run failed: unable to write frame N (t = ...)` and exit code 1 (no plotting). A NaN that reaches TNL's adaptivity error estimate would make Kutta–Merson retry the same step forever (NaN comparisons are false, so the step is neither accepted nor shrunk; TNL's `max` is `std::max`, which passes a NaN on or not depending on the operand order), and a collapsed step stops the time: so `time_stepping` counts the attempts in a row whose first stage has the same `t` (stage 0 is evaluated at the solver time) and after `max_attempts_at_same_time` (100; healthy runs reject 1–3 steps in thousands) throws `SolverStuck`, the only way out of TNL's loop. `run` catches it around `solve()`, saves the last accepted `u` as `info/stuck_state.npy` (`write_state`, frame format, kept out of `calculations/`), records the reason with the NaN/inf counts and exits with 2 like above. The steps are counted: accepted ones from `solver.getIterations()` (reset by every `solve()`, so summed over the frames), rejected ones as RHS evaluations / `Method::getStages()` minus accepted (`time_stepping` counts its calls on the host). The progress line shows them per frame, `parameters.txt` the total (`Integration steps: N (rejected: M)`).

**Precision:** `Real` is `float` (`include/core/types.hpp`, since 5e9bccb), also in the `.npy` frames. All GPU arithmetic is written with `Real` (`Real(…)` literals, integer exponents as `Real(n)`), so switching back to `double` is a one-line change. Float vs double on the 200×200 zirconium run differed by 3.5e-4 in the phase after 100 frames and was ~13× faster on an RTX 2070 SUPER.

**GPU constraints:** the model and `InitialCondition` are captured **by value** in device lambdas. Any method called from the RHS, BCs or IC must be `__cuda_callable__`, and their members end up on the device, so they hold only plain data: `Grid`, `BoundaryConditions` and `Anisotropy` (`include/config/Parameters.hpp`), the model's own `Params` and numbers. `Parameters` itself (strings, run settings, the model's config section as JSON) and `ConfigSection` stay on the host. A model does not change after construction, so its methods are `const`. No `virtual` methods: an object copied from the host would carry a pointer to the host vtable onto the GPU. Lambdas use `--extended-lambda`, and the build uses relocatable device code (`-rdc=true`, needed because the kernels in `main.cu` call device functions defined in other `.cu` files) with device link-time optimization (`-dlto`), which inlines device functions across `.cu` files at link time. Without `-dlto` every such call was a real call: the RHS kernels needed 92 registers on sm_86 instead of 39–41 and 300–460 bytes of stack; adding it (2026-11-20, test and bench Dlto_*) gave bitwise identical results and 2.0–2.8× on an RTX 3060, 1.5–4.1× on an RTX 2070 SUPER. Keep `-dlto` (and check the register counts, `cuobjdump --dump-resource-usage`, if the kernels get slower after a change).

**Models (`include/models/Model.hpp` and its child classes):** the choice of model is static (compile time), not virtual. `main` compares `model.type` from the config with each model's `name` and calls `start<ModelT>`, which reads the model's physical parameters (`ModelT::Params::load`, before anything is written), creates the run folder, writes the setup, builds the model and `u`, sets the initial condition (`set_initial_condition` in `src/initial_condition/InitialCondition.cu`: from the file or from code, then the boundary conditions) and calls `run(parameters, model, u, run_folder)`, which only does the time loop and writes the frames; so each model gets its own GPU kernels. The list of what a model provides is at the top of `Model.hpp`: `name`, a nested plain-data `struct Params` (with `static load(json)` and `entries()` for `parameters.txt`/`.tex`), a constructor `(const Parameters&, const Params&)` and `set_rhs_at(u, fu, i, j)` (interior points); the rest is inherited.
- `Model` (`src/models/Model.cu`) is the base class with only what all models share. Its constructor `(parameters)` is protected, so only the child classes are constructed. It holds `grid` and `bound_cond` (`BoundaryConditions` in `Parameters.hpp`: the boundary conditions, common to all models, a copy of `Parameters::bound_cond`), and has `phase_at`/`conc_at`, the boundary conditions for both fields and the degrees of freedom (2 N).
- The anisotropic Allen–Cahn operator for the phase is **copied** into both models (the user's choice: it is not expected to change much; keep the two copies the same): `get_rhs_phase_at(u, i, j, F)` = `(1/alpha) * (div T0(grad p) + f_0/ksi^2 - (b/ksi) * p^2(p-1)^2 * F)` for the model's force-term value `F`, with `grad_p_*`, `div_T0`, `T0_1/2`, `f_0`, `grade_4_polynom`. `T0` contains the anisotropy `psi(theta) = 1 + A cos(m(theta - theta_0))` (`Anisotropy` in `Parameters.hpp`, shared with the Wulff IC). Its parameters (`alpha`, `par_a`, `par_b`, `ksi` and `anisotropy`, an `Anisotropy`) are fields of each model's own `Params`, deliberately not a shared struct (the user's choice: the planned models will not have them); each `Params::load` reads them (also a copy, with the checks `m >= 2` and the convexity condition `A <= 1/(m^2-1)`), and `start` passes `ksi` and `anisotropy` to the initial condition (`ksi` for `HyperbolicTangent`, the anisotropy for `WulffShape`). It finds them with the trait `has_phase_interface` (`main.cu`: `Params` has members `ksi` and `anisotropy`); for a model without them it passes zeros and refuses those two initial conditions from code (config error, before the run folder is created).
- `AllenCahn` (`src/models/AllenCahn.cu`, `model.type` `allen_cahn`; its section: `alpha`, `a`, `b`, `ksi`, `A`, `m`, `theta_0`, `force_term` `constant` (with `force_size`) or `radial` (no size)): the verification cases with analytic solutions (a shrinking circle or Wulff shape). Its `F(i, j)` is the prescribed force, and the concentration RHS is 0.
- `ZrNbChoud2013` (`src/models/ZrNbChoud2013.cu`, `model.type` `Zr-Nb_Choud2013`, called `zirconium` until 2026-11-18; its section: `alpha`, `a`, `b`, `ksi`, `A`, `m`, `theta_0`, `d`, `T`): `F` = `G_m_alpha - G_m_beta`, and the concentration evolves by `div(D grad c) + div(D_p grad p)`.
- `ZrHMa2002` (`src/models/ZrHMa2002.cu`, `model.type` `Zr-H_Ma2002`, hydrides in Zr–H after Ma et al. 2002, one orientation variant; its section: `C1`, `C2`, `A1`, `A2`, `A3`, `alpha`, `beta`, `L_p`, `M`, `c_init_hydride`, `c_init_matrix`, all floating-point, `alpha`/`beta`/`L_p`/`M` not negative): equations since 2026-11-23, written out in the header. The phase is the order parameter φ (time-dependent Ginzburg–Landau), `∂φ/∂t = L_p (α Δφ − A2 (C − C2) φ + A3 φ³ − A3 φ⁵)`, the concentration is the hydrogen content (Cahn–Hilliard, fourth order), `∂C/∂t = M Δμ`, `μ = A1 (C − C1) + A2/2 φ² − β ΔC`. **The field is rescaled** (the user's choice): the article's φ is k·φ with k² = A3/A4 of the article, so the hydride is φ = 1 at C = C2 (≈ 1 near it; −1 is a hydride too, f depends on φ²) and the coefficients of φ⁴/4 and φ⁶/6 are equal, so there is no `A4`; the article's values (C1 0.05, C2 0.58, A1 60, A2 −20, A3 10, A4 3.5, α = β = 3.5, L_p = M = 0.4, grid units Δx = 1) become A2 = −57.142857, A3 = 81.632653, α = 10, L_p = 0.14 (C1, C2, A1, β, M unchanged), in `config/Zr-H_Ma2002.json` and `tests/configs/hydride.json`; a NumPy check gave the article's solution divided by k to 1e-15. Setting A4 = A3 without rescaling A2, α, L_p would change the physics (matrix solubility 0.104 → 0.41). Not included from the article: elastic energy, noise, variants 2–3 (A5–A7). The user's first derivation had both signs flipped and C1 instead of C2 in the A2 term; the article's PDF text layer drops minus signs (A2 = −20, −L_p in eq. 6), checked against its Fig. 1. Discretisation: 5-point Laplacians, μ recomputed at the 4 neighbours (13-point stencil for C), μ on the boundary = μ at the neighbouring interior point (`chemical_potential_at` clamps the index: the no-flux condition ∂μ/∂n = 0 next to the Neumann condition for C), so the sum of C over the interior is conserved; `check_parameters` refuses Dirichlet for the concentration (a fixed boundary concentration with the no-flux μ was not thought through). Checked 2026-11-23 with a NumPy copy of the scheme (scratchpad only): stable, interior mass conserved to 1e-14, energy decreasing; the interface is only ~2–3 cells wide at Δx = 1, and a flat 1D interface gives bulk C 0.129 / 0.617 at h = 1 but 0.1037 / 0.5798 at h = 0.5 (common tangent 0.104 / 0.58), so use h ≤ 0.5 (explicit step ≈ 0.01·h⁴). ICs from code get the concentrations `c_init_hydride` (phase 1) and `c_init_matrix` (phase 0) from the config (article: 0.58 and 0.1; 0.1 is below the matrix solubility, so small seeds may dissolve). The plotters assume φ ∈ [0, 1] with the interface at 0.5, which fits the rescaled field. Not yet compiled or run on the GPU when written.
- All models share the state vector of two fields (phase, concentration). The output (`(2, sizeY, sizeX)` frames), the IC code and the Python plotters assume it too. A model with a different number of fields is planned but needs those generalised first.
- Thermodynamic data of an alloy system live in a plain-data struct per system in `models/thermodynamics/` (2026-11-23; before, free functions of `T` in `include/models/constants.hpp`, which every GPU thread re-evaluated at every point in every RHS evaluation). `ZrNbThermodynamics` (Zr–Nb: CALPHAD-style Gibbs energies, diffusivities, mobilities): fixed numbers are `static constexpr Real` members (`c_init_alpha/beta`, `L_0_alpha`), the values that depend only on `T` are members (`RT`, `G_*_0`, `L_0_beta`, `L_0_i_beta`, `M_Nb_alpha/beta`) computed once by the host-only constructor `ZrNbThermodynamics(double T)` from host functions in double (namespace `from_T` in the `.cu`), and the functions of the concentration (`G_m_alpha(c)`, `G_m_beta(c)`) are `__cuda_callable__` methods. `ZrNbChoud2013` builds its member `thermo` from `own.T` in its constructor (declared after `own`), so it goes to the GPU with the model. It brought no speedup (bench Thermo_bench, RTX 2070 SUPER: 0.96–1.03×, same step counts; the per-point functions of T were not the bottleneck) and changed the Zr–Nb results by rounding (test Thermo_test: max |Δconc|/range 1.3e-4 after 5 frames, same α cell counts). The constants the solver does not use (`delta`, `molar_volume`, `sigma`, `M_phi`, `epsilon_tilde`, …) are kept commented out in the `.cu` (the user's choice). `constants::R` and `Cal_to_joule` (`core/constants.hpp`) are `double`, for the host precomputation only. A Zr–H system gets its own struct next to it, built the same way; a shared base class only once there is something to share (the user's choice: no base for one struct).

**Config (`Parameters::load`):** one JSON file per run. `Parameters` reads `solver`, `init_cond` and `bound_cond` (the boundary conditions, common to all models). The section `model` holds `type` (the model's `name`) and one section per model, `model.<type>`, with that model's physical parameters as flat keys (see the header of each model class, and `config/<model>.json`); only the chosen one is read, so a config can keep the sections of several models (the configs in `config/` keep only their own). Any other top-level section is an error. Every section the solver reads (`solver`, `solver.domain`, `init_cond`, `bound_cond`, `model.<type>`) is read strictly by `ConfigSection` (`include/config/ConfigSection.hpp`): every key is required (no defaults, also `integration_time_step` when `custom_integration_time_step` is false), types are checked (an integer has to be written without a decimal point, a bool as `true`/`false`), and a key nobody read is an error too (`The config entry ... is unknown`: a typo, a parameter of another model). Until 2026-11-23 unknown keys were only a warning, because `test`/`bench` gave every commit the same configs, and cf625cb, which made them an error, then refused every config with a key added later (`solver.adaptivity`; test Adaptivity); now each commit gets the configs of its time (config sets, see Regression test). `Parameters::load` also checks sizeX, sizeY >= 3, frame_num >= 1, final_time > initial_time, x_right > x_left, y_right > y_left and a positive custom step. `radius_proportion` is scaled by the shorter side of the domain; it is read as double and multiplied in double before the rounding to `Real`, as before the strict reading (reading it as `Real` would change the radius in the last bit).
- Until 2026-11-18 the physical parameters were in the top-level sections `problem` (`alpha`, `beta` (unused), `a`, `b`, `d`, `T`, `ksi`), `force_term` (`type` `zirconium`/`constant`/`radial`, `size`) and `anisotropy`. Since 2026-11-23 nothing reads that layout or other old results any more (the user's choice: no backward compatibility, it cluttered the code): `migrate_config.py`, which converted it, is deleted, the solver refuses such a config for its unknown sections, `Dataset` reads only `info/setup/config.json`, and `compare_runs.py`, `compare_times.py` and `run_case` only `info/setup/parameters.txt`. Only `tests/config_sets/up_to_12df4ec` keeps the old sections, for `test`/`bench` against the commits that read them.

**Output layout for `results/<FOLDER>/`:**
- `calculations/Result-NNNNN.npy`: the only output format. Array of shape `(2, sizeY, sizeX)` of `Real` (phase, then concentration; x and y are not stored, they are computed from the config). Written and read by `write_frame` / `read_frame` in `src/io/ResultIO.cu` (using `include/external/npy.hpp`), read in Python by `python/dataset.py`. (A text format `x y phase conc` existed until 2026-11-11 and was removed.)
- `info/setup/`: written by the binary at the start, through `RunFolder` (`src/io/RunFolder.cu`), which holds the C++ side of the folder layout (`calculations/`, `info/setup/`, `parameters.txt`) and writes the run information.
  - `parameters.txt`: the parameters, then the run date (start time), computer (host name, e.g. `gp11`) and GPU (written by the binary at the start), one `Warning: ...` line per warning of `warn()` so far (it keeps the warnings from before the folder existed; none come that early since unknown config keys became errors; a warning at the end of the run is appended there too), the number of integration steps and the computation time (written at the end, in this order: "Computation time" marks a finished run for `cluster.sh`) and the git commit (appended by `make run`). A run that stopped on NaN/inf, a stuck solver or a frame it could not write has `Run failed: <reason>` instead of the steps and the time (`cluster.sh list` shows it as `failed`).
  - `config.json`: a copy of the config, which the Python plotters read.
  - `parameters.tex`
  - `sources.tar.gz`: only for cluster runs, the exact sources the job compiled (with uncommitted changes and the config).
  - `mode.txt`: only for cluster jobs, `run`, `test` or `bench` (written by `run.sbatch`; tests and benchmarks also keep `baseline.tar.gz`).
- `info/plots/`: frames (`.jpg`) and animations (`.mp4`/`.gif`) from the Python plotters.
- `info/boundary/`: `interface_num.crv` and `interface_anal.crv` from `write_boundary_files`.
- The paths of the three subfolders are defined once in `Dataset` (`setup_folder`, `plots_folder`, `boundary_folder`); on the C++ side the paths are in `RunFolder`. The Makefile (`PARAM_PATH`), `tests/common.sh` and `tests/benchmark.sh` also know where `parameters.txt` is.

**Python (`python/plotter.py`):** `Plotter` base class with `BoundaryPlotter2D` (draws the 0.5-level contour, which can be overlaid with the analytic circle or Wulff boundary), `SurfacePlotter` (3D) and `CutPlotter` (1D cut). Scales do not depend on the model or the domain units (2026-11-23; before, the concentration was fixed to [0, 0.09] for Zr–Nb, and the 3D height and the cut aspect were in domain units, so the 64×64 Zr–H domain came out flat): the value range of a field is its min/max over all frames (`Dataset.value_range`, all frames read once), always including 0 (and 1 for the phase), the same for every frame of an animation (the cut used to rescale per frame); the colour map uses the bare min/max over all frames (`colour_limits`, without adding 0, for contrast), the 3D z axis and the cut y axis add 10 %; the 3D box height is `SURFACE_HEIGHT` (phase 1, concentration 0.5) × the longer side of the domain, the cut box is square (`CUT_BOX_ASPECT`). The boundary computation does not live in the plotters: `python/boundary.py` has the class `Boundary` (numerical curves from contourpy, analytic curves) and `write_boundary_files`, which `basic_plot.py` calls once to write `info/boundary/interface_num.crv` and `interface_anal.crv` for all frames (the files are always rewritten from scratch; `plot.py` never writes them). `python/cli.py` is shared by `basic_plot.py` and `plot.py`: it holds the common arguments, `decide_drawing` (whether to draw concentration plots and the analytic boundary, from the model, its force term and the `initial_condition` name) and `build_plotters`.

## Common extension points

- **New initial condition:**
  1. Add it to `ICType` in `include/config/enums.hpp`, before `Count`.
  2. Add both string conversions in `src/config/enums.cu`.
  3. Add a `case` in `InitialCondition::get_phase` (and `get_concentration` if needed) in `src/initial_condition/InitialCondition.cu`.
  4. If it has an analytic solution, add its name to `ANALYTIC_INITIAL_CONDITIONS` and handle it in `analytic_polyline` (both in `python/boundary.py`; `decide_drawing` in `python/cli.py` uses the list).
- **New model** (same two fields):
  1. Write a child class of `Model` in `include/models/<Name>.hpp` + `src/models/<Name>.cu`, named after the model without a `Model` suffix (like `AllenCahn`, `ZrNbChoud2013`) (the Makefile compiles every `.cu` under `src/`), following the list at the top of `Model.hpp`: `static constexpr const char* name` (its config name, e.g. `"my_model"`), a nested `struct Params` of plain data (`Real` fields) with `static Params load(const nlohmann::json&)` (read it with `ConfigSection`, end with `check_all_read()`) and `std::vector<ParameterEntry> entries() const` and `InitialConcentrations initial_concentrations() const` (the concentrations of the ICs from code where the phase is 1 and 0, also the value outside a scaled file IC and the Dirichlet value; `Parameters.hpp`; from constants like `ZrNbChoud2013`/`AllenCahn` or from the config like `ZrHMa2002`; `start` passes them to `set_initial_condition`), a public constructor `(const Parameters&, const Params&)` that stores the `Params` in a member, and `__cuda_callable__ void set_rhs_at(...) const`. Copy the phase operator from an existing model if the phase follows the anisotropic Allen–Cahn equation. If the model cannot work with some run settings (e.g. boundary conditions), give it its own `static void check_parameters(const Parameters&)` that throws; it hides `Model`'s empty one and `start` calls it before the run folder is created. `start` in `main.cu` passes `model_params.ksi` and `model_params.anisotropy` to the initial condition if `Params` has them (`has_phase_interface`), otherwise refuses `HyperbolicTangent` and `WulffShape`. Document its config section in the header comment.
  2. Add one `if (parameters.model_type == Name::name) return start<Name>(...)` line in `main` (`src/main.cu`) and its name to the error message there.
  3. Add its complete config `config/<name>.json` (named after `name`, so `MODEL=<name>` finds it) and a regression test config in `tests/configs/` (and teach `decide_drawing` in `python/cli.py` and the helpers in `python/dataset.py` about it if it plots differently).
- **New physical parameter of a model:** a field in the model's `Params` (if it belongs to the phase equation of both current models, in both), read in its `load` and listed in its `entries()`; add it to the configs of that model (`config/<model>.json`, `tests/`; HEAD then refuses the new key, so first save the current test configs as a config set, see Regression test). Nothing else changes.
- **New run setting** (solver, initial condition, boundary conditions): add a field in `include/config/Parameters.hpp` (floating-point fields are `Real`, not `double`, so that a `float` build does no double arithmetic on the GPU), then read it in `Parameters::load` (with the section's `ConfigSection`, before its `check_all_read()`; the key is then required, so add it to every config: `config/*.json`, `tests/configs/`, `tests/benchmark_configs*/`; HEAD then refuses the new key, so first save the current test configs as a config set, see Regression test). Also add it to `save_human_readable` and `save_for_latex` so runs stay self-documenting. A new boundary condition goes into `BoundaryConditions` (`include/config/Parameters.hpp`, the member `bound_cond` of `Parameters`), which the model and `set_init_cond_boundary` already receive; another setting the GPU code needs goes into the members of `InitialCondition` (for an IC) or of the model.
- **Initial condition from file:** with `init_cond_from_file: true`, the path is resolved relative to the run's `calculations/` folder and the file must be a `Result-*.npy` frame of float or double (converted to `Real`; the shape must be `(2, sizeY, sizeX)`). `scaling: true` embeds every second point of it (a grid with half the resolution) into the centre of the domain. The code is `set_init_cond_from_file` in `src/initial_condition/InitialCondition.cu`. Afterwards `set_init_cond_boundary` overwrites the edge values of the file to satisfy the boundary conditions (like for an IC from code).
