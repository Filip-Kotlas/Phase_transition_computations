# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

CUDA/C++17 phase-field solver for a 2D phase transition (anisotropic Allen–Cahn-type equation for the phase `p`, coupled with diffusion of the Nb concentration `c` in a Zr–Nb alloy). It is research code for a thesis at FNSPE CTU Prague. Python scripts post-process and plot the results. Comments and messages are in English.

## Build & run

The code needs `nvcc` and the header-only **TNL** library (Template Numerical Library). The build uses the system TNL in `/usr/include/TNL`; the Makefile's `-I~/.local/include` is never tilde-expanded, so it does nothing (on the cluster `~/.local/include/TNL` is an old 2022 copy without `ODESolver.h`, so "fixing" the tilde would break the build). Builds only work on a Linux machine with an NVIDIA GPU. The Makefile compiles with `-arch=native` (override with `make CUDA_ARCH=...`) and keeps objects in `build/sm_<compute capability>/`, so build on the machine that will run the binary. Jobs for the GPU cluster are submitted from a local machine with `slurm/cluster.sh` (see `slurm/run.sbatch`); from Windows PowerShell use the launcher `.\slurm\cluster.cmd`, which runs the script with Git's bash and Windows OpenSSH (the key lives in the Windows ssh-agent).

```bash
make                                  # build ./build/Phase-field
make run FOLDER=MyRun                 # build, run with config/config.json -> results/MyRun, then plot
make run FOLDER=MyRun DELETE_CALCS=1  # same, but keep only the first and last Result-*.npy afterwards
make run_all                          # run every comp_configurations/*.json (each one is copied over config/config.json)
make clean
```

- The binary is called as `Phase-field [result_folder [config_file]]`; the config defaults to `config/config.json` (`make run CONFIG=...` overrides it). `slurm/cluster.sh submit` uploads the sources of each run (including `config/config.json`) to `jobs/<FOLDER>/sources.tar.gz` on the cluster. The job unpacks them into the node's `/tmp`, builds them from scratch and runs `make run` there, with `results` linked to the shared results folder. A queued job therefore always runs the code it was submitted with, and jobs share no sources or build.
- Run everything from the repo root. The binary resolves its default config through a relative path, and the Python scripts look in `./results/<name>`.
- Header dependencies are tracked: nvcc writes `build/sm_XX/*.d` (`-MMD -MP`) and the Makefile includes them, so changing a header under `include/` recompiles the objects that use it. System headers (TNL in `/usr/include`) are not tracked. `make clean` is still needed after changing compiler flags in the Makefile or after updating TNL (not on the cluster, where every job builds from scratch). (Before this, stale `.o` files after header changes caused hard-to-find bugs.)
- `make run_all` overwrites the tracked `config/config.json`. `comp_configurations/` is gitignored, apart from `.gitkeep`.
- There is no linter. There is a regression test and a benchmark (see below).

## Regression test

It answers "did my change alter the results?", not "are the results correct?" (that is the job of a comparison with the analytic solutions).

```bash
.\slurm\cluster.cmd test MyTest                     # working tree (uncommitted changes) vs HEAD
.\slurm\cluster.cmd test MyTest --against HEAD~1    # vs any commit, e.g. after committing the changes
.\slurm\cluster.cmd test MyTest --against A --new B # two commits: B is tested instead of the working tree
.\slurm\cluster.cmd status                          # while it runs: which build or run it is at
.\slurm\cluster.cmd log                             # the result; also in results/MyTest/report.txt
```
- `cluster.sh test` uploads the working tree (like `submit`) plus `git archive <commit>` as the baseline, and refuses when both have the same code (`config/config.json` does not count). So test **before** committing, or use `--against`.
- `--new COMMIT` (test and bench) uploads that commit as `new.tar.gz` and tests it instead of the working tree. The working tree is still uploaded as the harness: `run.sbatch`, `tests/`, the configs and `python/compare_*.py` always come from it (`harness_dir` in `tests/common.sh`), so commits from before the test existed can be compared too, as long as they accept `Phase-field RESULT_FOLDER CONFIG` and today's configs.
- The job (`run.sbatch` with `MODE=test`, time limit 1 h) runs `tests/regression.sh`: it builds both versions, runs every `tests/configs/*.json` with both on the same GPU (so GPU-type differences cannot appear) into `results/MyTest/{base,new}/<case>`, then runs `python/compare_runs.py`. Nothing is stored in the repo; the baseline is recomputed every time. The configs, scripts and comparison come from the new version.
- Cases (5 frames, seconds each): `circle_constant` (isotropic, constant force; 120×100 on [0, 1.5] × [0, 1], so hx ≠ hy and a mistake in the IC coordinates shows), `wulff_radial` (anisotropy, Wulff IC, radial force), `zirconium` (the `Zr-Nb_Choud2013` model, concentration), `dirichlet_mixed` (Dirichlet and Neumann for both fields), `from_file` (IC from a float32 `.npy` file with `scaling`, generated by `tests/prepare_input.py`), these four 100×100 on the unit square; `random_rectangle` (120×80 on [-0.5, 1.5] × [0.2, 1]; random values at every point from `random.npy`, without scaling, zirconium, all Neumann). The other cases start with a constant phase near the edges, so a wrong boundary index would barely show in them (during the run the interface tail reaches the bottom edge in `circle_constant` and the grain reaches the edges in `zirconium`, so the boundary treatment does affect them); `random_rectangle` catches it (`prepare_input.py` writes random values for any `random*.npy`). Keep at least one case with hx ≠ hy, otherwise swapped x and y go unnoticed. Each case should run a different code path; add a config for a new feature.
- Verdicts: IDENTICAL (bitwise), CLOSE (phase difference and concentration difference relative to its range ≤ `--tol`, default 1e-4, and no cell crossed 0.5), DIFFERENT, FAILED (missing, unfinished or NaN), INCOMPATIBLE (different grids). Cleanup should give IDENTICAL; reordered arithmetic (performance work) at best CLOSE. For reference, float vs double on the 200×200 zirconium run differed by 3.5e-4 in the phase after 100 frames.
- The test draws no plots. After `cluster.cmd fetch MyTest`, `python3 python/basic_plot.py --name MyTest` plots every run in it (it does that for any `--name` folder that is not a run itself but contains runs); one case: `--name MyTest/new/zirconium`.
- `python3 python/compare_runs.py results/A results/B` compares any two runs (or two folders of runs) the same way, e.g. two `submit` runs on different GPUs.

## Benchmark

It answers "how much faster is my change?". Built like the regression test: working tree vs a baseline commit, both on the same GPU, nothing stored in the repo.

```bash
.\slurm\cluster.cmd bench MyBench                          # working tree vs HEAD, 3 runs of each version per case
.\slurm\cluster.cmd bench MyBench --against HEAD~1 --repeat 5 --gpu rtx3060
.\slurm\cluster.cmd bench MyBench --against 5e9bccb~1 --new 5e9bccb   # two commits, e.g. an old change
.\slurm\cluster.cmd bench MyBench --long                   # one demanding case, one ~10 min run of each version
.\slurm\cluster.cmd log                                    # the result; also in results/MyBench/report.txt
```
- The job (`run.sbatch` with `MODE=bench`, time limit 1 h + 15 min per run above 3) runs `tests/benchmark.sh`: it builds both versions and runs every `tests/benchmark_configs/*.json` N times with each, alternating the order (base new, new base, …), so a drift on the node hits both alike. `tests/common.sh` holds the build and run functions shared with `regression.sh`.
- Time = the solver's own `Computation time` from `parameters.txt` (time loop including frame writing, without start-up and IC). Baselines older than 98e885c do not write it; then the wall time of the process is used for that case (marked `*`). `python/compare_times.py` reports median (fastest–slowest) per version and the speedup base/new (> 1: new is faster; `~` = the ranges overlap, i.e. within the noise), and the geometric mean over the cases. It also reads `Integration steps` from each run's `parameters.txt` (`-` for versions from before the step count, i.e. up to 2f0ab0f) and shows the steps of both versions and the per-step speedup (time per accepted step, base/new), so a speedup from fewer adaptive steps can be told from cheaper steps; it notes when the repetitions of one version took different numbers of steps.
- Output in `results/MyBench/`: `times.csv` (every run), `report.txt`, `{base,new}/<case>` (first run, complete) with `comparison.txt` from `compare_runs.py` (a speedup only counts if the results still agree), `repeats/` (the other runs, without frames).
- Cases (about half a minute each on an RTX 2070 SUPER, scaled from Bench_noise, where the runs of one case differed by ≤ 1 %): `zirconium_200` (the production config, shortened: the time per frame is constant during a run), `zirconium_400` (the same at 400×400), `wulff_radial_300` (anisotropy and radial force, no concentration; the Wulff shape shrinks and would vanish at t ≈ 0.055, so its length comes from the resolution, not from `final_time`). The time scales linearly with `final_time` and roughly as h^-3.5 with the grid.
- `--long` runs `tests/benchmark_configs_long/*.json` instead (passed on as `BENCH_SET=long`): `zirconium_400_sharp` (zirconium at 400×400 with a thin interface, `ksi` 0.0125 instead of 0.075, `theta_0` 0.1, `final_time` 0.02, 4 frames; measured 8.7–8.9 min per run on an RTX 2070 SUPER in LongBench, about 130 s per frame. The grain grows into a cross that almost touches the edges at t = 0.02, so do not lengthen `final_time`: raise the resolution instead), once with each version by default (`--repeat N` for more), time limit 30 min + 30 min per repetition, timeout per run 40 min instead of 10. It shows whether a speedup holds for a long, demanding run.
- Unlike `test`, `bench` runs when both versions have the same code: that shows the noise. Times depend on the GPU type, so compare speedups, or use `--gpu` to benchmark on the same type.

Plotting (it runs from the repo root and needs `results/<name>/info/setup/config.json`):
```bash
python3 python/basic_plot.py --name MyRun --type both   # selected frames + animations (mp4, or gif without ffmpeg) into results/MyRun/info/plots/
python3 python/basic_plot.py --name MyRun --frames 0 50 last --format gif
python3 python/plot.py --name MyRun --frame 10 --type phase   # --frame last works too, --no-save opens a window instead of saving
```
`python/graphs/*.py` are standalone scripts for thesis figures. They use LaTeX text rendering.

## Architecture

**Source layout:** `include/` and `src/` have the same subfolders, by function: `core/` (`types.hpp`, `Grid.hpp`), `config/` (`Parameters`, `ConfigSection`, `enums`), `models/` (`Model`, `AllenCahn`, `ZrNbChoud2013`, the Zr–Nb `constants.hpp`), `initial_condition/` (`InitialCondition`), `io/` (`ResultIO`, `RunFolder`) and, only in `include/`, `external/` (the third-party `json.hpp`, `npy.hpp`); `src/main.cu` stays at the top. Headers are included with their folder, relative to `include/` (`#include "models/Model.hpp"`, also for `json.hpp`). The Makefile finds the sources in all subfolders and mirrors them in `build/sm_XX/`; a new `.cu` file needs no Makefile change.

**Data flow:** `config/config.json` → `Parameters::load` → a model (`AllenCahn` or `ZrNbChoud2013`) + `InitialCondition` → TNL `ODESolver` (adaptive Kutta–Merson) loop in `src/main.cu` → `write_frame` (`src/io/ResultIO.cu`) → `results/<FOLDER>/calculations/Result-NNNNN.npy` → Python plotters.

**State vector:** there is a single TNL `Vector` `u` of length `2*sizeX*sizeY` that lives on the CUDA device. Phase values are in `[0, N)` and concentration values in `[N, 2N)`, with `N = sizeX*sizeY` and linear index `j*sizeX + i`. Use `Model::phase_at` / `conc_at` to read them.

**Grid (`include/core/Grid.hpp`):** a plain struct with `sizeX`, `sizeY`, `domain` and the steps `hx`, `hy` (computed once by its constructor), plus `num_points()` (= N), `index(i, j)` and the coordinates `x(i)`, `y(j)`. It is built from the config by `Parameters::grid()`, held by the model and `InitialCondition` and passed to `write_frame`/`read_frame` and the IC setters. Use it instead of writing the index arithmetic or computing h again.

**Time stepping (`main.cu`):** the RHS lambda is evaluated with `parallelFor` on interior points only. Boundary conditions are separate `parallelFor`s that run after it and set only `fu` on the boundary: Dirichlet `fu = 0`, Neumann `fu` = the `fu` of the neighbouring interior point. They never write `u` (the solver passes temporary stage vectors to the RHS, so writes into `u` would lag one time step). This keeps the boundary consistent only if it is consistent at the start, so `set_init_cond_boundary` (`src/initial_condition/InitialCondition.cu`) applies the boundary conditions to the initial condition (Dirichlet values: phase 0, concentration `c_init_beta`); bottom/top run before left/right in both places, so the corners match. The outer loop counts frames (`i = 1..frame_num`, so it always ends, whatever the rounding of the solver time): it sets the stop time `initial + (final-initial)*i/frame_num` (computed from `i` in double, exactly `final_time` for the last frame), solves up to it and writes one file per frame. Frame numbers are absolute, `round(initial_time/timeStep) + i` with `timeStep = (final-initial)/frame_num`, so a run continued from a file carries on with the numbering; the progress line counts `i`. Unless `custom_integration_time_step` is set, the integration step defaults to `min(hx,hy)^2/5`; it is only the initial step, Kutta–Merson then adapts it with TNL's default tolerance (main.cu does not set the adaptivity). After every written frame (and the initial one) `check_frame_finite` counts NaN/inf values on the GPU (one reduction per field); if there are any, it writes `Run failed: ...` into `parameters.txt` and the binary exits with `EXIT_RUN_FAILED` (2), keeping the broken frame. `make run` then still appends the commit and plots with `--force` (basic_plot.py refuses incomplete runs otherwise), skips `DELETE_CALCS` and fails with 2; any other non-zero exit stops `make run` at once. A frame that `write_frame` cannot write (full disk, quota, missing folder) also stops the run, with `Run failed: unable to write frame N (t = ...)` and exit code 1 (no plotting). A NaN that reaches TNL's adaptivity error estimate would make Kutta–Merson retry the same step forever (NaN comparisons are false, so the step is neither accepted nor shrunk; TNL's `max` is `std::max`, which passes a NaN on or not depending on the operand order), and a collapsed step stops the time: so `time_stepping` counts the attempts in a row whose first stage has the same `t` (stage 0 is evaluated at the solver time) and after `max_attempts_at_same_time` (100; healthy runs reject 1–3 steps in thousands) throws `SolverStuck`, the only way out of TNL's loop. `run` catches it around `solve()`, saves the last accepted `u` as `info/stuck_state.npy` (`write_state`, frame format, kept out of `calculations/`), records the reason with the NaN/inf counts and exits with 2 like above. The steps are counted: accepted ones from `solver.getIterations()` (reset by every `solve()`, so summed over the frames), rejected ones as RHS evaluations / `Method::getStages()` minus accepted (`time_stepping` counts its calls on the host). The progress line shows them per frame, `parameters.txt` the total (`Integration steps: N (rejected: M)`).

**Precision:** `Real` is `float` (`include/core/types.hpp`, since 5e9bccb), also in the `.npy` frames. All GPU arithmetic is written with `Real` (`Real(…)` literals, integer exponents as `Real(n)`), so switching back to `double` is a one-line change. Float vs double on the 200×200 zirconium run differed by 3.5e-4 in the phase after 100 frames and was ~13× faster on an RTX 2070 SUPER.

**GPU constraints:** the model and `InitialCondition` are captured **by value** in device lambdas. Any method called from the RHS, BCs or IC must be `__cuda_callable__`, and their members end up on the device, so they hold only plain data: `Grid`, `BoundaryConditions` and `Anisotropy` (`include/config/Parameters.hpp`), the model's own `Params` and numbers. `Parameters` itself (strings, run settings, the model's config section as JSON) and `ConfigSection` stay on the host. A model does not change after construction, so its methods are `const`. No `virtual` methods: an object copied from the host would carry a pointer to the host vtable onto the GPU. Lambdas use `--extended-lambda`, and the build uses relocatable device code (`-rdc=true`), so device functions in different `.cu` files are not inlined into each other.

**Models (`include/models/Model.hpp` and its child classes):** the choice of model is static (compile time), not virtual. `main` compares `model.type` from the config with each model's `name` and calls `start<ModelT>`, which reads the model's physical parameters (`ModelT::Params::load`, before anything is written), creates the run folder, writes the setup, builds the model and `u`, sets the initial condition (`set_initial_condition` in `src/initial_condition/InitialCondition.cu`: from the file or from code, then the boundary conditions) and calls `run(parameters, model, u, run_folder)`, which only does the time loop and writes the frames; so each model gets its own GPU kernels. The list of what a model provides is at the top of `Model.hpp`: `name`, a nested plain-data `struct Params` (with `static load(json)` and `entries()` for `parameters.txt`/`.tex`), a constructor `(const Parameters&, const Params&)` and `set_rhs_at(u, fu, i, j)` (interior points); the rest is inherited.
- `Model` (`src/models/Model.cu`) is the base class with only what all models share. Its constructor `(parameters)` is protected, so only the child classes are constructed. It holds `grid` and `bound_cond` (`BoundaryConditions` in `Parameters.hpp`: the boundary conditions, common to all models, a copy of `Parameters::bound_cond`), and has `phase_at`/`conc_at`, the boundary conditions for both fields and the degrees of freedom (2 N).
- The anisotropic Allen–Cahn operator for the phase is **copied** into both models (the user's choice: it is not expected to change much; keep the two copies the same): `get_rhs_phase_at(u, i, j, F)` = `(1/alpha) * (div T0(grad p) + f_0/ksi^2 - (b/ksi) * p^2(p-1)^2 * F)` for the model's force-term value `F`, with `grad_p_*`, `div_T0`, `T0_1/2`, `f_0`, `grade_4_polynom`. `T0` contains the anisotropy `psi(theta) = 1 + A cos(m(theta - theta_0))` (`Anisotropy` in `Parameters.hpp`, shared with the Wulff IC). Its parameters (`alpha`, `par_a`, `par_b`, `ksi` and `anisotropy`, an `Anisotropy`) are fields of each model's own `Params`, deliberately not a shared struct (the user's choice: the planned models will not have them); each `Params::load` reads them (also a copy, with the checks `m >= 2` and the convexity condition `A <= 1/(m^2-1)`), and `start` passes `ksi` and `anisotropy` to the initial condition (`ksi` for `HyperbolicTangent`, the anisotropy for `WulffShape`).
- `AllenCahn` (`src/models/AllenCahn.cu`, `model.type` `allen_cahn`; its section: `alpha`, `a`, `b`, `ksi`, `A`, `m`, `theta_0`, `force_term` `constant` (with `force_size`) or `radial` (no size)): the verification cases with analytic solutions (a shrinking circle or Wulff shape). Its `F(i, j)` is the prescribed force, and the concentration RHS is 0.
- `ZrNbChoud2013` (`src/models/ZrNbChoud2013.cu`, `model.type` `Zr-Nb_Choud2013`, called `zirconium` until 2026-11-18; its section: `alpha`, `a`, `b`, `ksi`, `A`, `m`, `theta_0`, `d`, `T`): `F` = `G_m_alpha - G_m_beta`, and the concentration evolves by `div(D grad c) + div(D_p grad p)`.
- All models share the state vector of two fields (phase, concentration). The output (`(2, sizeY, sizeX)` frames), the IC code and the Python plotters assume it too. A model with a different number of fields is planned but needs those generalised first.
- Physical constants and thermodynamic functions for Zr–Nb (CALPHAD-style Gibbs energies, diffusivities, mobilities) are in `include/models/constants.hpp`.

**Config (`Parameters::load`):** one JSON file per run. `Parameters` reads `solver`, `init_cond` and `bound_cond` (the boundary conditions, common to all models). The section `model` holds `type` (the model's `name`) and one section per model, `model.<type>`, with that model's physical parameters as flat keys (see the header of each model class, and `config/config.json`); only the chosen one is read, so a config can keep the sections of several models. Any other top-level section only gets a warning on stderr (it is not read). The model sections are read strictly by `ConfigSection` (`include/config/ConfigSection.hpp`): every key is required (no defaults), types are checked (an integer has to be written without a decimal point), and keys nobody read are an error (typos, parameters of another model). `solver`, `init_cond` and `bound_cond` are still read with `.value(key, default)`, so a typo there silently gives the default. `radius_proportion` is scaled by the shorter side of the domain.
- Until 2026-11-18 the physical parameters were in the top-level sections `problem` (`alpha`, `beta` (unused), `a`, `b`, `d`, `T`, `ksi`), `force_term` (`type` `zirconium`/`constant`/`radial`, `size`) and `anisotropy`. The solver refuses such a config and names `python3 python/migrate_config.py FILE...`, which converts it in place. Results computed before keep the old layout in `info/setup/config.json`; the Python side reads both (`model_type`, `force_term` and `anisotropy` in `python/dataset.py`). The configs in `tests/` (regression and benchmark) keep the old sections next to `model` on purpose, so `test`/`bench` against commits from before the change still work: the old code reads the old sections, the new code reads `model` and warns that the others are not used. Keep both in agreement when changing a parameter there (with the old layout, `force_term.type` stays `zirconium`). Only the commits 2d32cad and 2ce1df9, which named the model `zirconium` in `model`, cannot read them.

**Output layout for `results/<FOLDER>/`:**
- `calculations/Result-NNNNN.npy`: the only output format. Array of shape `(2, sizeY, sizeX)` of `Real` (phase, then concentration; x and y are not stored, they are computed from the config). Written and read by `write_frame` / `read_frame` in `src/io/ResultIO.cu` (using `include/external/npy.hpp`), read in Python by `python/dataset.py`. (A text format `x y phase conc` existed until 2026-11-11 and was removed.)
- `info/setup/`: written by the binary at the start, through `RunFolder` (`src/io/RunFolder.cu`), which holds the C++ side of the folder layout (`calculations/`, `info/setup/`, `parameters.txt`) and writes the run information.
  - `parameters.txt`: the parameters, then the run date (start time), computer (host name, e.g. `gp11`) and GPU (written by the binary at the start), the number of integration steps and the computation time (written at the end, in this order: "Computation time" marks a finished run for `cluster.sh`) and the git commit (appended by `make run`). A run that stopped on NaN/inf, a stuck solver or a frame it could not write has `Run failed: <reason>` instead of the steps and the time (`cluster.sh list` shows it as `failed`).
  - `config.json`: a copy of the config, which the Python plotters read. `Dataset` falls back to `info/config.json` for results computed before the subfolders existed.
  - `parameters.tex`
  - `sources.tar.gz`: only for cluster runs, the exact sources the job compiled (with uncommitted changes and the config).
  - `mode.txt`: only for cluster jobs, `run`, `test` or `bench` (written by `run.sbatch`; tests and benchmarks also keep `baseline.tar.gz`).
- `info/plots/`: frames (`.jpg`) and animations (`.mp4`/`.gif`) from the Python plotters.
- `info/boundary/`: `interface_num.crv` and `interface_anal.crv` from `write_boundary_files`.
- The paths of the three subfolders are defined once in `Dataset` (`setup_folder`, `plots_folder`, `boundary_folder`); on the C++ side the paths are in `RunFolder`. The Makefile (`PARAM_PATH`), `tests/common.sh` and `tests/benchmark.sh` also know where `parameters.txt` is.

**Python (`python/plotter.py`):** `Plotter` base class with `BoundaryPlotter2D` (draws the 0.5-level contour, which can be overlaid with the analytic circle or Wulff boundary), `SurfacePlotter` (3D) and `CutPlotter` (1D cut). The boundary computation does not live in the plotters: `python/boundary.py` has the class `Boundary` (numerical curves from contourpy, analytic curves) and `write_boundary_files`, which `basic_plot.py` calls once to write `info/boundary/interface_num.crv` and `interface_anal.crv` for all frames (the files are always rewritten from scratch; `plot.py` never writes them). `python/cli.py` is shared by `basic_plot.py` and `plot.py`: it holds the common arguments, `decide_drawing` (whether to draw concentration plots and the analytic boundary, from the model, its force term and the `initial_condition` name) and `build_plotters`.

## Common extension points

- **New initial condition:**
  1. Add it to `ICType` in `include/config/enums.hpp`, before `Count`.
  2. Add both string conversions in `src/config/enums.cu`.
  3. Add a `case` in `InitialCondition::get_phase` (and `get_concentration` if needed) in `src/initial_condition/InitialCondition.cu`.
  4. If it has an analytic solution, add its name to `ANALYTIC_INITIAL_CONDITIONS` and handle it in `analytic_polyline` (both in `python/boundary.py`; `decide_drawing` in `python/cli.py` uses the list).
- **New model** (same two fields):
  1. Write a child class of `Model` in `include/models/<Name>.hpp` + `src/models/<Name>.cu`, named after the model without a `Model` suffix (like `AllenCahn`, `ZrNbChoud2013`) (the Makefile compiles every `.cu` under `src/`), following the list at the top of `Model.hpp`: `static constexpr const char* name` (its config name, e.g. `"my_model"`), a nested `struct Params` of plain data (`Real` fields) with `static Params load(const nlohmann::json&)` (read it with `ConfigSection`, end with `check_all_read()`) and `std::vector<ParameterEntry> entries() const`, a public constructor `(const Parameters&, const Params&)` that stores the `Params` in a member, and `__cuda_callable__ void set_rhs_at(...) const`. Copy the phase operator from an existing model if the phase follows the anisotropic Allen–Cahn equation. `start` in `main.cu` passes `model_params.ksi` and `model_params.anisotropy` to the initial condition, so a model without them needs that call adjusted. Document its config section in the header comment.
  2. Add one `if (parameters.model_type == Name::name) return start<Name>(...)` line in `main` (`src/main.cu`) and its name to the error message there.
  3. Add a regression test config in `tests/configs/` (and teach `decide_drawing` in `python/cli.py` and the helpers in `python/dataset.py` about it if it plots differently).
- **New physical parameter of a model:** a field in the model's `Params` (if it belongs to the phase equation of both current models, in both), read in its `load` and listed in its `entries()`; add it to the configs of that model (`config/config.json`, `tests/`). Nothing else changes.
- **New run setting** (solver, initial condition, boundary conditions): add a field in `include/config/Parameters.hpp` (floating-point fields are `Real`, not `double`, so that a `float` build does no double arithmetic on the GPU), then read it in `Parameters::load`. Also add it to `save_human_readable` and `save_for_latex` so runs stay self-documenting. A new boundary condition goes into `BoundaryConditions` (`include/config/Parameters.hpp`, the member `bound_cond` of `Parameters`), which the model and `set_init_cond_boundary` already receive; another setting the GPU code needs goes into the members of `InitialCondition` (for an IC) or of the model.
- **Initial condition from file:** with `init_cond_from_file: true`, the path is resolved relative to the run's `calculations/` folder and the file must be a `Result-*.npy` frame of float or double (converted to `Real`; the shape must be `(2, sizeY, sizeX)`). `scaling: true` embeds every second point of it (a grid with half the resolution) into the centre of the domain. The code is `set_init_cond_from_file` in `src/initial_condition/InitialCondition.cu`. Afterwards `set_init_cond_boundary` overwrites the edge values of the file to satisfy the boundary conditions (like for an IC from code).
